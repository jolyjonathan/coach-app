# Audit complet — Coach Adaptatif

**Date :** 11 juin 2026
**Périmètre :** backend Go (15 fichiers), frontend (app.js + modules scientifiques, SPA admin, service worker), config déploiement (Docker, Caddy, CI), suite de tests.
**Méthode :** lecture intégrale du code, `go vet`, `go build`, `go test`, exécution des tests JS (`tests/run-tests.js`).

---

## Verdict rapide

Le code est **mûr et sérieux** côté sécurité : 2FA TOTP avec anti-replay, sessions opaques 256 bits, CSRF double-submit + SameSite=Strict, chiffrement AES-GCM at-rest, RGPD (consentement art. 9, opt-out art. 22, export art. 20, effacement art. 17 backups inclus), journal d'audit avec rotation 12 mois, conteneur distroless `read_only` + `cap_drop ALL`. La plupart des points d'audit historiques (H-02, H-03, M-01…M-06, L-01…L-04) sont déjà traités et tracés dans les commentaires.

**Mais il y a un problème bloquant immédiat : la suite de tests ne compile pas, donc la CI ne teste rien.** Plusieurs bugs de calibration et quelques fuites mineures complètent le tableau.

Priorisation : 🔴 à corriger d'abord · 🟠 important · 🟡 amélioration.

## 🔴 Bloquants (à régler en premier)

### B1 — La suite de tests Go ne compile pas
`contains(s, sub string) bool` est déclaré **deux fois** : `middleware_test.go:151` et `totp_test.go:83`. Résultat :

```
./totp_test.go:83:6: contains redeclared in this block
    ./middleware_test.go:151:6: other declaration of contains
FAIL coach [build failed]
```

`go test ./...` échoue à la compilation. Concrètement **l'étape `go test -race` de la CI est rouge à chaque run**, et comme le job `docker` a `needs: go`, l'image n'est jamais validée non plus. La CI ne protège donc plus rien.

**Fix :** supprimer l'une des deux définitions (en faire un helper partagé, ex. dans `testhelpers_test.go`). Vérifié : après suppression du doublon, le paquet compile.

### B2 — `TestDeleteAccount` cassé (test obsolète vs. handler)
Après correction de B1, le test échoue :
```
auth_test.go:187: delete-account: status=400 body=map[error:JSON invalide]
```
`handleDeleteAccount` exige désormais un body `{ "password": "..." }` (durcissement légitime contre le vol de session), mais le test envoie un body `nil`. Le test n'a pas suivi l'évolution du handler. **Le test est faux, pas le code** — mais tant qu'il l'est, la CI restera rouge même après B1.

**Fix :** mettre à jour le test pour POSTer le mot de passe courant.

### B3 — Suite flaky / pollution d'état global entre tests
`TestAdminRevokeSessions` **passe en isolé mais échoue dans le run complet**. Les maps de package (`usersByID`, `usersByEm`, `sessions`, `totpLastUsed`, `rlMap`) sont des globales partagées ; sans reset systématique entre tests, l'ordre d'exécution (aléatoire sur les maps) crée des interférences.

**Fix :** un helper `resetGlobalState(t)` appelé via `t.Cleanup()` dans `newTestServer`, qui vide toutes les maps globales.

## 🟠 Sécurité — failles réelles

### S1 — Le secret du webhook physio fuite dans les access logs
Route : `POST /api/physio/webhook/{uid}/{secret}`. Le secret 32-hex et le `uid` sont **dans le chemin de l'URL**. Or `accessLog` (middleware.go) logge `r.URL.Path` à chaque requête :
```go
log.Printf("%s %s %s %d %s", clientIP(r), r.Method, r.URL.Path, ...)
```
Le commentaire promet « never body, headers, or cookies » — vrai, mais le secret n'est dans aucun des trois : il est dans le **path**. Quiconque lit les logs (journald, driver json-file Docker, Caddy access.log) récupère un credential réutilisable qui contourne l'auth de session.

**Fix au choix :** (a) passer le secret en header `X-Coach-Webhook-Secret` au lieu du path ; (b) ou, a minima, masquer le segment secret dans `accessLog` pour les chemins `/api/physio/webhook/`. Note : le `verify_token` Strava, lui, est en query string — non loggé (le middleware logge `Path`, pas `RawQuery`) — donc OK.

### S2 — Troncature bcrypt à 72 octets non gérée
`validPassword` autorise jusqu'à 128 caractères, mais bcrypt **ignore silencieusement tout au-delà de 72 octets**. Un mot de passe de 80 caractères et un autre partageant les 72 premiers octets sont équivalents à la connexion. Impact faible (il faut un mot de passe très long et un attaquant connaissant le préfixe) mais c'est un piège classique.

**Fix :** soit capper à 72 octets dans `validPassword`, soit pré-hasher (`sha256` → base64) avant bcrypt pour préserver toute l'entropie.

### S3 — Rate-limit login par IP uniquement
`/api/login` est limité à 8/15 min **par IP**. Un credential-stuffing distribué (botnet, rotation d'IP) contourne entièrement la limite, et il n'existe pas de compteur par compte ni de lockout. Acceptable pour une app auto-hébergée mono/few-users, mais à noter si l'instance est exposée publiquement.

**Fix :** ajouter un compteur d'échecs par `emailLower` (avec back-off), en plus du per-IP.

### S4 — `clientIP` derrière proxy fait confiance au premier maillon de XFF
Avec `COACH_TRUST_PROXY=1`, `clientIP` prend `parts[0]` de `X-Forwarded-For`. C'est correct **avec Caddy** (qui réécrit l'en-tête proprement), mais si un jour un autre proxy est mis devant qui *append* au lieu de réécrire, le premier élément redevient spoofable par le client → bypass du rate-limit. Dépendance implicite à la config Caddy.

**Fix :** documenter explicitement l'exigence « le proxy doit réécrire (pas append) XFF », ou prendre le dernier hop de confiance.

### S5 — `style-src 'unsafe-inline'` résiduel dans la CSP
Déjà connu et tracé (audit M-02) : ~380 attributs `style="…"` générés dans `app.js` imposent `style-src-attr 'unsafe-inline'`. Le `style-src-elem 'self'` strict capture déjà la moitié du bénéfice. Reste une surface d'exfiltration CSS en cas de XSS. Migration vers classes = chantier hors-scope mais souhaitable.

> Points **intentionnels** vérifiés et acceptables : enumeration d'email sur `/register` (UX assumée, login timing-safe via `dummyHash`), absence de flow SMTP « mot de passe oublié » (reset admin documenté), anti-replay TOTP in-memory (fenêtre résiduelle 90 s post-reboot assumée).

## 🟠 Bugs fonctionnels & incohérences de modèle

### F1 — Unités de charge incohérentes dans le modèle Banister
`banister.js > sessionLoad` mélange deux échelles :
- séance muscu : `sets × RPE` → une séance type (5 sets, RPE 7) = **35**
- séance externe (course, etc.) : `durationMin × RPE` → un footing 30 min RPE 7 = **210**

Soit un facteur **~6× en faveur du cardio** dans le même CTL/ATL/TSB. Dès qu'un utilisateur logge des activités externes (ou des imports Strava), sa fatigue/forme est dominée par le cardio et le TSB devient peu lisible — ce qui contredit l'objectif affiché « CTL/ATL dans les ranges TrainingPeaks classiques ». C'est la faille de calibration la plus impactante côté science.

**Fix :** unifier l'échelle. Soit normaliser le cardio (`durationMin × RPE / 6` pour le ramener au range muscu), soit passer la muscu aussi en durée estimée × RPE. À calibrer pour qu'une séance « moyenne » de chaque type donne une charge comparable.

### F2 — `fetchOuraReadiness` est du code mort
La fonction est définie, documentée… et retourne **toujours `(nil, nil)`** sans jamais être appelée ailleurs dans le code. Le fallback HRV via `daily_readiness` annoncé dans les commentaires n'existe donc pas réellement.

**Fix :** soit la câbler comme fallback dans `handlePhysioSync` quand `fetchOuraSleep` ne renvoie pas de HRV, soit la supprimer pour ne pas laisser croire qu'elle fait quelque chose.

### F3 — Agrégation HRV Oura : « moyenne pondérée » qui n'en est pas une
Dans `fetchOuraSleep`, le commentaire annonce une moyenne HRV pondérée par durée, mais le code fait :
```go
if e.HRV == 0 || s.TotalSleepDuration > 0 { e.HRV = s.AverageHRV }
```
→ c'est un simple « dernière session avec durée > 0 gagne » (last-wins), pas une pondération. Pour un utilisateur avec sieste + nuit, le HRV retenu est arbitraire selon l'ordre du payload.

**Fix :** accumuler `Σ(hrv·durée)/Σ(durée)` si l'on veut vraiment une pondération.

### F4 — `stravaActivityToPhysio` : l'estimation d'énergie de secours promise n'existe pas
Le commentaire évoque « sinon estimation grossière duration×HR à partir de moving_time », mais le `switch` n'a **que** les branches `Calories` et `Kilojoules`, sans `default`. Une course sans capteur de puissance ni Strava Premium ressort donc avec `ActiveEnergy = 0` — elle ne contribue qu'au `AvgHR`. Cohérent une fois F1 réglé, mais l'écart code/commentaire est trompeur.

### F5 — `parseAppleHealthAutoExport` : mindful en minutes supposées
`mindfulSec += qty * 60` suppose que AHAE pousse des **minutes**. Si l'export est déjà en secondes (variable selon la config AHAE), la durée de méditation est multipliée par 60. Champ « étendu » non consommé par les modèles aujourd'hui, donc impact nul à court terme, mais faux dès qu'il sera exploité.

### F6 — Agrégation par jour en UTC (décalage de fuseau)
`isoDayFromAHAE` et `fetchOuraSleep` découpent la date sur les 10 premiers caractères d'un timestamp **UTC**. Une mesure à 01:00 heure locale (ex. UTC+2 → 23:00 UTC la veille) est rattachée au mauvais jour. Marginal pour HRV/sommeil de nuit, mais peut décaler `readiness` d'un jour aux frontières.

## 🟡 Améliorations (dette & robustesse)

**Build & supply-chain**
- Épingler les images Docker par digest SHA256 (déjà tracé M-01, `scripts/pin-images.sh` existe — reste à l'exécuter et committer). Les tags `golang:1.22-alpine` et `distroless/static-debian12:nonroot` restent mutables.
- Le binaire compilé `coach` (10 Mo) et `coach-go-tmp-umask` traînent dans le repo de travail ; bien ignorés par `.gitignore`, à supprimer du dossier local.

**Tests**
- Après B1–B3 : ajouter des tests sur les modules JS scientifiques côté Go n'est pas nécessaire (`tests/run-tests.js` couvre science.js — 83 passent), mais aucun test ne couvre `banister.js` ni `bayesian.js`. Vu leur rôle central, ajouter des cas (TSB connu, forecast Kalman monotone, anti-outlier Huber).
- La couverture Go ne teste ni Strava ni physio (les deux plus gros fichiers). Au minimum tester `parseAppleHealthAutoExport` et `mergePhysioIntoData` (parsing + cap 2000).

**Sécurité (durcissement)**
- Rotation de `COACH_TOKEN_KEY` : le format `ENC:v1:` est versionné mais aucun chemin `v2`/ré-encryption sur rotation n'existe. Documenter ou implémenter une procédure de rotation.
- Gérer l'event Strava `aspect_type=delete` et les events `athlete` (deauthorization) — le `TODO` en strava.go:606 laisse des tokens stale après révocation côté Strava.
- HSTS : envisager `preload` si le domaine est dédié.

**Fonctionnel**
- `saveSessions()`/`saveUsers()` sont lancés en `go …` à chaque create/destroy de session : sous charge, beaucoup de snapshots+rename redondants du même fichier. Un debounce (flush au plus toutes les N s, comme le snapshotter rate-limit) réduirait les I/O.
- Le `.bak` quotidien de `writeJSONAtomic` ne se déclenche que si le fichier cible a >24 h ; pour `users.json` (écrit souvent), le backup peut ne quasiment jamais se rafraîchir. Découpler la stratégie de backup de la fréquence d'écriture.

## Ce qui est solide (à conserver)

- Architecture auth : copie des champs sous `usersMu.RLock()` avant `RUnlock()` pour éviter les data races (bien fait partout, y compris `handleMe`, `handleLogin`).
- 2FA TOTP fait main, RFC 6238, drift ±1, **anti-replay par counter monotone** — propre.
- Défense session fixation (destruction du sid présenté avant d'en émettre un neuf) sur register, login, change-password.
- Admin : impossible de se self-démote, de supprimer le dernier admin, ou de se supprimer soi-même ; tout est audité.
- Validation chemin (`validUserID` regex) en défense en profondeur même si l'id vient toujours du serveur.
- Gate RGPD art. 9 dupliquée côté serveur ET sur le webhook (pas de contournement par client scripté).
- `num()` dans la SPA admin neutralise une XSS indirecte via données utilisateur non validées en profondeur — réflexe rare et juste.
- Conteneur : distroless, `read_only`, `tmpfs:/tmp`, `cap_drop: ALL`, `no-new-privileges`, limites CPU/mémoire, healthcheck via sous-mode du binaire (pas de curl embarqué).
